# Конституция проекта Appsmith

> Операционная копия конституции для Spec Kit (v1.0.0, ратифицирована 20.09.2026). Рабочий слой с историей — Obsidian, карточка «Конституция проекта» (папка «Управление»). Изменения — через `/speckit.constitution` с обоснованием версии (semver).

## Core Principles

### I. Один источник правды — каркас

Каркас-приложение `Appsmith_AF` (репозиторий `spb-gku-cad/Appsmith_AF`, ветка `main`) — источник правды по приложению. Всё, что можно показывать, живёт в нём. Никакая ветка, форк или локальная копия не объявляется источником правды вместо `main`.

### II. Изменения каркаса — только через PR из форка

В Appsmith Community Edition ветки через интерфейс недоступны, поэтому параллельная работа строится на схеме «основной репозиторий + форк»:

- работа в форк-приложении `Appsmith_AF_fork` (`v.kotov/Appsmith_AF_fork`) → **Commit & Push** → **Pull Request** в основной → merge → **Pull** в основном приложении;
- обратная синхронизация — «Sync fork» на GitVerse + **Pull** в форке;
- рядовые правки разработчика — прямо в `main`, крупные/рискованные работы — во временном форке с PR;
- перед началом работы — Pull, после — Push.

### III. Файлы репозиториев руками не править (кроме разрешённого в форке)

Формат файлов репозитория Appsmith специфичный: ручные правки ломают приложение и дают конфликты. Правило:

- Изменения приложения — через редактор Appsmith + git-sync («Commit & Push»).
- Внешние правки ассистента (18.09.2026, решение пользователя) допустимы **только в локальной копии форка**: тела SQL-запросов (`query.txt`), их `metadata.json`, JSObjects (`.js`), создание/удаление целых файлов запросов и виджетов.
- `widgets/*.json` — только удаление файлов и правки по образцам из git-песочницы **с явного согласования** пользователем (риск сломать DSL).
- После внешних правок в форке: ассистент коммитит локально → push делает пользователь → **в редакторе Appsmith сначала Pull, потом Commit & Push** (иначе Appsmith зальёт своё старое состояние поверх внешних правок).
- Общие файлы (`application.json`, тема, datasources) — зона единоличной ответственности.
- Каркас `Appsmith_AF` меняется только через редактор + PR из форка; локальная копия каркаса — только `fetch`/`pull` для анализа.

### IV. БД версионируется снапшотами

База данных сама не версионируется — фиксируются выгрузки в репозитории `Appsmith_DB` (`spb-gku-cad/Appsmith_DB`):

- снапшот **до и после** каждого изменения структуры БД или справочников;
- каждый снапшот — набор файлов `00_*`–`08_*` в **корне** репозитория + отдельный коммит `Снапшот <дата>`;
- историю хранит git, сравнение версий — `git diff <хеш Снапшота N-1>..<хеш Снапшота N>`;
- набор запросов для выгрузки — заметка «Схема БД» (Obsidian, `Разработка/Данные и БД/`);
- при изменении фактической схемы актуализируется страница Grammax 51 «Структура БД» — сразу в репозитории `PROCESS_DOC_GITVERSE`.

### V. Каждая работа завершается проверкой и фиксацией

Работа не считается завершённой, пока не выполнены оба пункта (DoD, «Регламент совместной разработки»):

- код закоммичен (для работ в Appsmith) — или правка внесена в заметки (для анализа);
- запись в журнал дня сделана (заметка на день в `Задачи/Appsmith/Журнал/`, создать новую, если сегодняшней нет).

## Порядок работы и контроля изменений

Ежедневный цикл («Регламент проверки изменений»):

- `git pull`/`fetch` по всем репозиториям (каркас, форк, `Appsmith_DB`, `PROCESS_DOC_GITVERSE`);
- выявление изменений: `git log` новых коммитов, `git diff --stat` по приложению (структура `pages/<страница>/{queries,jsobjects,widgets}/`, `datasources/*.json`, `jslibs/`), diff снапшотов БД, сверка форка с основным;
- фиксация в журнале дня строки проверки: `Проверка изменений: Appsmith_AF <хеш> (<дата>), Appsmith_AF_fork <хеш> (<дата>), Appsmith_DB <хеш> (<дата>)`;
- при вычистке (удалении/переносе) — короткая пометка 1–2 строки в журнале.

## Документация и публикация

- Контент страниц ведётся **сразу в Grammax** (`PROCESS_DOC_GITVERSE`, контент — `pererabotka-appsmith/`, корень git — папкой выше): требования (20), описание функционала (15.7), страницы приложения (40–46), данные и БД (50–53).
- Obsidian (`Задачи/Appsmith/`) — рабочий/служебный слой: хаб, индексы, журнал, протоколы, регламенты, справка по коду, БД-артефакты.
- Перед правкой Grammax-репозитория — `git pull`; правки коммитятся в него же; **`git push` — только после явного согласования с пользователем** (решение от 19.09.2026). Кнопка «Синхронизировать» в Grammax — тот же pull/push через интерфейс приложения.
- Страница 51 «Структура БД» — единственная, которая обновляется сразу в репозитории Grammax без рабочего слоя Obsidian.

## Governance

- Настоящая конституция имеет приоритет над прочими неформальными практиками; при конфликте действующее правило берётся из разделов выше, а расхождение фиксируется в журнале.
- Версионирование конституции — по semver: MAJOR — удаление/переопределение принципа; MINOR — новый принцип или существенное расширение; PATCH — уточнения формулировок.
- Изменения конституции вносятся через `/speckit.constitution` с обоснованием версии; ратифицирует пользователь (владелец проекта), после этого обновляется операционная копия в форке и рабочий слой Obsidian.
- Изменение регламента или инструкций ассистента («AGENTS.md») → проверить конституцию на расхождение (обычно PATCH-правка); изменение принципа → сначала конституция, потом регламенты.
- Каждое предложение PR и каждый артефакт Spec Kit (`spec.md`, `plan.md`, `tasks.md`) проверяются на соответствие принципам I–V; нарушения фиксируются в ревью.
