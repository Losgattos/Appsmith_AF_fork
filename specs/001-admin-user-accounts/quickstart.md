# Quickstart: Администрирование — проверка фичи

**Feature**: `001-admin-user-accounts` | **Date**: 2026-09-20 (актуализировано 23.09.2026)

Сценарии проверки end-to-end. Выполняются в редакторе Appsmith (форк), данные сверяются в БД `appsmith_2.0` через psql или страницу Grammax 51.

**Prerequisites**: страница «Администрирование» открыта под администратором; запросы `get_users`, `get_user_roles`, `get_directory_inn` выполняются on page load; **в редакторе сделан Pull** (форма с 22.09.2026 — отдельные виджеты: `userLogin`, `userPassword` (PASSWORD), `userINN`, `userINNName`, `userRole`, `userEnabled`, `userButtonSave`/`userButtonClose`; кнопки удаления — `delButtonNO`/`delButtonYES`/`delCaption`).

> **Важно (решение пользователя 22.09.2026):** пароль обязателен **и при добавлении, и при редактировании** (валидация в `saveUser()`); кнопка «Сохранить» (`userButtonSave`) неактивна при пустых обязательных полях (логин/пароль/ИНН/роль).
> **Учреждение — кейс A «Я знаю ИНН»:** поле `userINN` — Text Input (10 цифр); при вводе ≥10 цифр `onInnChange()` ищет учреждение, `userINNName` показывает название или «Учреждение не найдено»; при сохранении — точное совпадение (`get_ou_by_inn`), 0 → «не найдено», >1 → «неоднозначен».

## Сценарий 1 — Просмотр списка (US1)

1. Открыть страницу — таблица `usersTable` загружена.
2. Проверить колонки: Логин, Роль, Учреждение, Активен, ИНН (`ou_inn`). **Видимой колонки пароля нет** (FR-001/SC-005; `u.password` в SELECT остаётся как скрытая колонка — нужен форме редактирования, см. T010).
3. Клик по строке — кнопки «Редактировать»/«Удалить» становятся доступными (FR-009).

## Сценарий 2 — Добавление пользователя (US2)

1. «Добавить» → `userModal` с пустой формой (поля очищены, «Активен» = вкл). (T023)
2. Пустая кнопка «Сохранить» (`userButtonSave`) **неактивна**, пока не заполнены логин/пароль/ИНН/роль.
3. Заполнить логин, пароль (Password Input), ИНН (10 цифр → `userINNName` показывает название), роль (Select), «Сохранить».
4. Пользователь появился в списке; вход по новому логину/паролю работает (SC-002).

## Сценарий 3 — Уникальность логина (FR-011)

1. В форме добавления ввести логин, уже существующий у другого пользователя.
2. Сохранение отклоняется: «Пользователь с таким логином уже существует», **форму не очищает** (точечный запрос `check_user_login`).
3. Редактирование пользователя без смены логина — проходит (собственная запись не считается дубликатом).

## Сценарий 4 — Редактирование (US3)

1. Выбрать строку → «Редактировать» → форма с текущими значениями (логин, пароль подставлен, ИНН + название учреждения в `userINNName`, роль, активность).
2. Сменить логин → вход по старому невозможен, по новому возможен (US3/AC1).
3. Пароль **обязателен** — при сохранении с пустым паролем отказ «Укажите пароль» (решение 22.09; US3/AC2 изменено: «пароль не трогать» больше не применяется — всегда вводится заново; хранится открытым текстом, замечание про хэширование остаётся).
4. Сменить роль → в списке новая роль (US3/AC3).

## Сценарий 5 — Блокировка (US4)

1. Отключить «Активен» (`userEnabled` Switch) → сохранить → сессии пользователя погашены (`UPDATE user_sessions`).
2. Вход заблокированного → «Учётная запись заблокирована» (FR-005).
3. Включить обратно → вход возможен (US4/AC3).

## Сценарий 6 — Удаление (US5)

1. Создать пользователя, не входить — удалить (`delButtonYES`): ок, запись исчезает (US5/AC1).
2. Войти пользователем → удаление → «Удалить нельзя: он входил в систему» (US5/AC3).
3. Пользователь с историей отчётов → «Удалить нельзя: у него есть история отчётов» (US5/AC2).
4. Edge case: сессии в прошлом (завершённые) всё равно блокируют удаление.

## Сценарий 7 — Пароль (US6)

1. Ввод пароля длиннее 11 символов или с недопустимым символом → отклонение «Пароль: 1–11 символов, только латиница и цифры» (FR-007, валидация в `saveUser()`).
2. Пустой пароль при добавлении и при редактировании → «Укажите пароль» (решение 22.09).
3. Вход с паролем, заданным администратором, — проходит (US6/AC2).
