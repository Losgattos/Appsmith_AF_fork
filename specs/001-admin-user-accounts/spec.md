# Feature Specification: Администрирование — управление учётными записями

**Feature Branch**: `001-admin-user-accounts`

**Created**: 2026-09-20

**Status**: Draft

**Input**: User description: "Администрирование: управление учётными записями пользователей (итерация 2). Администратор просматривает список учётных записей, добавляет новых пользователей, редактирует логин/роль/учреждение/активность/пароль в одном модальном окне, блокирует/разблокирует, удаляет пользователя (только если он никогда не входил и у него нет истории отчётов). Пароли не показываются; хэширование отложено. Список — на нативной таблице."

## Clarifications

### Session 2026-09-20

- Q: Уникален ли логин пользователя? → A: Да, логин должен быть уникальным. При попытке добавить или отредактировать пользователя с уже существующим логином сохранение отклоняется, и система показывает сообщение «Пользователь с таким логином уже существует». (Решение пользователя 20.09.2026.)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Просмотр списка учётных записей (Priority: P1)

Администратор открывает страницу администрирования и видит список всех учётных записей: логин, учреждение, роль, статус активности. Пароли на экран не выводятся. Список сортируемый и фильтруемый, с постраничным выводом.

**Why this priority**: Это базовая видимость — без неё остальные сценарии (добавление, редактирование, удаление) невозможно адресовать к конкретной записи.

**Independent Test**: Может быть полностью проверен открытием страницы под учётной записью администратора: список загружается, каждая строка соответствует фактической записи в базе, поля роли и учреждения читаемые.

**Acceptance Scenarios**:

1. **Given** администратор с правами на страницу, **When** он открывает страницу «Администрирование», **Then** отображается список учётных записей с колонками логин, учреждение, роль, активность — без колонки пароля.
2. **Given** список загружен, **When** строка выбрана кликом, **Then** она подсвечивается и кнопки «Редактировать»/«Удалить» становятся доступными.

---

### User Story 2 - Добавление нового пользователя (Priority: P1)

Администратор нажимает «Добавить», открывается модальное окно с пустой формой: логин (обязателен), учреждение (обязательно, из справочника), роль (обязательна, из справочника), пароль (обязателен для нового пользователя), активность (по умолчанию активен). После сохранения пользователь появляется в списке и может войти по заданным данным.

**Why this priority**: Добавление учётных записей — основная операция администрирования (заводятся новые учреждения/пользователи); без неё система не масштабируется.

**Independent Test**: Создание пользователя через форму и проверка входа по новому логину/паролю без участия администратора.

**Acceptance Scenarios**:

1. **Given** открыта форма добавления, **When** заполнены логин, учреждение, роль и пароль и нажато «Сохранить», **Then** пользователь появляется в списке и входит в систему по заданным данным.
2. **Given** форма добавления, **When** логин не заполнен или пуст после обрезки пробелов, **Then** сохранение отклоняется с сообщением «Укажите логин».
3. **Given** форма добавления, **When** пароль не заполнен, **Then** сохранение отклоняется с сообщением о том, что для нового пользователя пароль обязателен.
4. **Given** форма добавления, **When** учреждение или роль не выбраны, **Then** сохранение отклоняется с соответствующим сообщением.
5. **Given** форма добавления, **When** введён логин, который уже есть у другого пользователя, **Then** сохранение отклоняется с сообщением «Пользователь с таким логином уже существует».

---

### User Story 3 - Редактирование пользователя (Priority: P1)

Администратор выбирает пользователя в списке, нажимает «Редактировать» — открывается то же модальное окно с текущими значениями. Можно изменить логин, учреждение, роль, статус активности и пароль (пустое поле пароля = не менять; текущий пароль не показывается). Изменения применяются одним сохранением.

**Why this priority**: Корректировка данных пользователя (смена логина, роли, перевод в другое учреждение) — повседневная операция; существовавшая в итерации 1 схема с отдельными кнопками заменяется единой формой.

**Independent Test**: Изменение логина пользователя и последующий вход по новому логину; смена роли отражается в списке и правах; пустой пароль не изменяет пароль.

**Acceptance Scenarios**:

1. **Given** выбран пользователь и открыто редактирование, **When** изменён логин и сохранено, **Then** вход по старому логину невозможен, по новому — возможен.
2. **Given** редактирование, **When** поле пароля оставлено пустым, **Then** пароль не меняется (вход по прежнему паролю работает).
3. **Given** редактирование, **When** изменена роль, **Then** в списке отображается новая роль, и доступные пользователю действия соответствуют новой роли.
4. **Given** редактирование, **When** логин изменён на логин, занятый другим пользователем, **Then** сохранение отклоняется с сообщением «Пользователь с таким логином уже существует».
5. **Given** редактирование, **When** логин не меняется и сохранение нажато, **Then** сохранение проходит (собственный логин не считается дубликатом).

---

### User Story 4 - Блокировка и разблокировка (Priority: P2)

Администратор может заблокировать учётную запись: заблокированный пользователь не может войти (вход отклоняется с сообщением об учётной записи), его активные сессии завершаются. Разблокировка восстанавливает вход.

**Why this priority**: Жизненный цикл учётных записей (уход сотрудника, компрометация) требует немедленного отключения доступа; это защитная операция.

**Independent Test**: Блокировка пользователя с активной сессией — после блокировки попытка входа отклоняется и активная сессия завершается.

**Acceptance Scenarios**:

1. **Given** пользователь заблокирован, **When** он пытается войти с корректным логином/паролем, **Then** вход отклоняется с сообщением «Учётная запись заблокирована».
2. **Given** пользователь блокируется, **When** у него есть активные сессии, **Then** все его активные сессии завершаются.
3. **Given** заблокированный пользователь, **When** администратор разблокирует его, **Then** вход по корректным данным снова возможен.

---

### User Story 5 - Удаление пользователя (Priority: P2)

Администратор выбирает пользователя, нажимает «Удалить», подтверждает в диалоге. Удаление возможно только если пользователь никогда не входил в систему (нет сессий) и у него нет истории отчётов; иначе система отказывает с указанием причины.

**Why this priority**: Очистка справочника от ошибочно заведённых записей важна, но защита от потери данных (история отчётов, сессии) приоритетнее самой операции.

**Independent Test**: Удаление пользователя, никогда не входившего, — успешно; удаление входившего или с историей — отказ с причиной, запись остаётся в базе.

**Acceptance Scenarios**:

1. **Given** пользователь никогда не входил и не имеет истории отчётов, **When** администратор подтверждает удаление, **Then** запись удаляется и исчезает из списка.
2. **Given** пользователь имеет историю отчётов, **When** администратор подтверждает удаление, **Then** удаление отклоняется с сообщением «у него есть история отчётов».
3. **Given** пользователь входил в систему, **When** администратор подтверждает удаление, **Then** удаление отклоняется с сообщением «он входил в систему».

---

### User Story 6 - Задание пароля администратором (Priority: P3)

Пароль задаёт администратор при создании/редактировании пользователя. Правила: от 1 до 11 символов, только латиница и цифры (единое правило с формой входа). Хэширование паролей отложено — хранение сохраняется как в существующей системе.

**Why this priority**: Без самостоятельной регистрации пароль — единственный способ дать пользователю доступ; правило формата — общее с входом.

**Independent Test**: Ввод пароля с недопустимым символом или длиннее 11 символов — отклонение с понятным сообщением; корректный пароль проходит.

**Acceptance Scenarios**:

1. **Given** ввод пароля, **When** пароль длиннее 11 символов или содержит неподдерживаемые символы, **Then** сохранение отклоняется с сообщением «Пароль: 1–11 символов, только латиница и цифры».
2. **Given** вход в систему, **When** используется пароль, заданный администратором, **Then** вход проходит (пароль применяется как есть, без дополнительного преобразования на этом шаге).

---

### Edge Cases

- Пользователь входил ранее, но сессии уже завершены (end_time в прошлом): удаление всё равно отклоняется (наличие любых записей сессий = «входил»).
- Дубликат логина при добавлении/редактировании: сохранение отклоняется, сообщение «Пользователь с таким логином уже существует» (уникальность логина — обязательное правило, подтверждено пользователем 20.09.2026).
- Поле учреждения со значением, отсутствующим в справочнике (например, запись с NULL) — отображается как пустое, редактирование требует выбора из справочника.
- Одновременное редактирование одного пользователя двумя администраторами — вне рамок (последнее сохранение побеждает).
- Попытка удалить выбранного пользователя без подтверждения (закрытие диалога) — ничего не удаляется.
- Блокировка и смена пароля в одном сохранении: сессии завершаются, если пользователь стал неактивен ИЛИ пароль изменён.
- Очень длинные логины/наименования учреждений — выводятся в полном виде (перенос строки в ячейке таблицы).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять администратору список учётных записей с полями: логин, учреждение, роль, статус активности; пароль в списке MUST NOT отображаться.
- **FR-002**: Система MUST позволять добавлять нового пользователя с обязательными полями: логин, учреждение, роль, пароль; активность по умолчанию — «активен».
- **FR-003**: Система MUST позволять редактировать пользователя: логин, учреждение, роль, статус активности; смена пароля — только при вводе нового значения (пустое поле = без изменений, текущий пароль не отображается).
- **FR-004**: Система MUST отклонять удаление пользователя, если существует хотя бы одна запись о его сессии или истории отчётов, и сообщать причину отказа.
- **FR-005**: Система MUST запрещать вход заблокированному пользователю с сообщением «Учётная запись заблокирована».
- **FR-006**: Система MUST завершать активные сессии пользователя при блокировке учётной записи или смене пароля.
- **FR-007**: Система MUST применять к паролю правило «1–11 символов, только латиница и цифры» (единое с формой входа) и отклонять несоответствующие значения с понятным сообщением.
- **FR-008**: Действия администратора по добавлению/редактированию/удалению/блокировке MUST выполняться в едином модальном окне и применяться одним сохранением (для добавления и редактирования).
- **FR-009**: Удаление и редактирование MUST требовать предварительного выбора строки в списке; без выбора соответствующие действия недоступны.
- **FR-010**: Система MUST сохранять перечисленные в определении фичи записи в базе так, как описано в ограничениях: наличие записей сессий и истории отчётов — единственные критерии отказа удаления.

- **FR-011**: Система MUST проверять уникальность логина при добавлении и редактировании и отклонять сохранение с сообщением «Пользователь с таким логином уже существует», если логин уже занят другой учётной записью (включая собственную запись при редактировании — сохранение без смены логина не считается дубликатом).

### Key Entities *(include if feature involves data)*

- **Учётная запись (пользователь)**: логин, пароль, роль, учреждение, статус активности. Связана с учреждением (справочник), ролью (справочник), сессиями, историей отчётов.
- **Учреждение**: элемент справочника (ИНН, короткое и полное наименование); пользователь привязан к одному учреждению.
- **Роль**: элемент справочника ролей (идентификатор, печатное и системное имя); определяет права пользователя.
- **Сессия**: запись о входе пользователя (идентификатор, время начала, время окончания); наличие сессии — признак «пользователь входил».
- **История отчётов**: записи о действиях пользователя с отчётами; наличие истории — запрет на удаление.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Администратор добавляет нового пользователя (открытие формы → сохранение) менее чем за 2 минуты.
- **SC-002**: 100% новых пользователей могут войти по заданным администратором данным без дополнительных действий со стороны администратора.
- **SC-003**: 100% попыток входа заблокированных пользователей отклоняются с понятным сообщением.
- **SC-004**: 100% попыток удаления пользователя с историей отчётов или сессиями завершаются отказом с указанием причины, запись остаётся в базе.
- **SC-005**: Ни в одном сценарии пароль пользователя не отображается на экране (ни в списке, ни в форме, ни в сообщениях).
- **SC-006**: Все операции итерации 2 выполняются через единое модальное окно; отдельные сценарии смены пароля/блокировки вне этого окна не требуются.

## Assumptions

- Аудит и журналирование действий администратора — вне рамок данной фичи (не требуется в текущем ТЗ).
- Хэширование паролей — отложено (решение 18.09.2026); хранение пароля остаётся как в существующей системе авторизации.
- Массовая (групповая) блокировка учётных записей — вне рамок итерации 2, решается отдельно.
- Страница «Администрирование» доступна только пользователям с ролью администратора; разграничение доступа использует существующий механизм ролей.
- Справочники ролей и учреждений не редактируются в рамках этой фичи.
- Существующий механизм сессий и входа (логин/пароль) переиспользуется без изменений протокола.
- Реализация происходит в низкокодовой среде (Appsmith) поверх существующего приложения; способы реализации вынесены в план и не могут противоречить конституции проекта (принципы I–V).
