# Implementation Plan: Администрирование — управление учётными записями

**Branch**: `001-admin-user-accounts` | **Date**: 2026-09-20 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/001-admin-user-accounts/spec.md`

## Summary

Итерация 2 административной страницы: единое модальное окно для добавления/редактирования пользователя (логин, учреждение, роль, пароль, активность), удаление с защитой по сессиям/истории, блокировка с гашением сессий. Базовая реализация уже собрана в форке (`save_user`/`delete_user`/`get_users` + JS `userAdmin` + виджеты) — план закрывает разрывы со спекой: **уникальность логина (FR-011)**, вывод `password` из списка (FR-001), поле учреждения в форме как Select, пароль как Password Input. Реализация: правила конституции III (в форке — тела SQL и JS, правки виджетов — в редакторе).

## Technical Context

**Language/Version**: Appsmith Community Edition (встроенный низкокодовый редактор; JS в JSObjects); datasource PostgreSQL `2.0`.

**Primary Dependencies**: Appsmith CE (git-sync на GitVerse), виджеты Table v2 / JSON Form / Modal / Select / Switch; без внешних библиотек.

**Storage**: PostgreSQL 16.15 (сервер `192.168.137.136:5432`, БД `appsmith_2.0`), схемы `appsmith` и `name_report_2026`. Структура меняется только через снапшоты (конституция IV).

**Testing**: Ручная проверка сценариев в редакторе (добавление → вход; редактирование; блокировка; удаление) + сверка ответов запросов через psql (при доступном VPN); автоматических тестов в проекте нет.

**Target Platform**: Веб-приложение (браузер), self-hosted Appsmith CE.

**Project Type**: Low-code web-приложение (Appsmith). НЕ порождает классический исходный код — артефакты это SQL/JS в репозитории форка (`pages/Администрирование/`).

**Performance Goals**: Список пользователей загружается при открытии страницы (Execute on page load); правки сохраняются за одно действие — дополнительных метрик не требуется.

**Constraints**: 
- Правки `widgets/*.json` — только через редактор Appsmith (конституция III); ассистент правит только SQL-тела/JS в локальной копии форка.
- БД не меняется в рамках этой фичи (ALTER не нужен) — уникальность логина обеспечивается на уровне приложения.
- Хэширование паролей отложено (решение 18.09.2026) — хранение как в существующей системе.

**Scale/Scope**: 1 страница «Администрирование» (в каркасе отсутствует — только форк); ~5 SQL-запросов, 1 JSObject, 3 виджета-контейнера.
