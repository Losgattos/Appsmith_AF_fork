# Research: Администрирование — управление учётными записями

**Feature**: `001-admin-user-accounts` | **Date**: 2026-09-20 | **Status**: Resolved

Факты собраны из: снапшотов `Appsmith_DB` (17.09.2026), карточки [[Администрирование (Учётные записи)]], фактического состояния форка `Appsmith_AF_fork` (коммиты `b952f67`, `8b5c2a4`), журнала дня.

## 1. Уникальность логина (FR-011)

**Decision**: Логин уникален; дубликат при добавлении/редактировании отклоняется с сообщением «Пользователь с таким логином уже существует» (решение пользователя 20.09.2026). Уникальность обеспечивается **на уровне приложения** (проверка в `saveUser()` перед `save_user.run()`), БД не меняется.

**Rationale**:
- В текущей схеме `appsmith.users` ограничения `UNIQUE` на `login` **нет** — только `users_pkey` на `id` (проверено по `Appsmith_DB/08_схема_ddl.sql`: `CREATE TABLE appsmith.users (id integer NOT NULL, directory_inn_id bigint NOT NULL, login text, ...)`, индексы — конституция IV, снапшот 17.09.2026).
- Добавление `UNIQUE`-констрейнта в БД = изменение структуры → требуется снапшот до/после и правка Grammax 51. Для итерации 2 это избыточно: дубликаты возможны только через саму админку, которая теперь же их и блокирует; объём данных мал (7 ролей, пользователей немного).
- Проверка в JS (по `get_users.data`, уже загруженному на странице) — минимальное изменение без новых запросов и миграций.

**Alternatives considered**: (1) `UNIQUE`-индекс в БД — отложено (миграция + снапшоты, см. Deferred Intents конституции); (2) проверка в SQL `save_user` (CTE `EXISTS`) — сложнее читать отказ из Appsmith и требует аккуратной обработки пустого `changed`.

## 2. Пароль в списке (FR-001/SC-005)

**Decision**: Из `get_users` убрать `u.password`.

**Rationale**: В фактическом `get_users.txt` форка присутствует `u.password` — противоречит FR-001 (пароль в списке MUST NOT отображаться) и создаёт риск утечки в `tableData`/devtools. Спека требует только `login, role, учреждение, активность` (+ скрытые `id`, `role_id`, `directory_inn_id`).

**Alternatives considered**: Скрыть колонку в таблице (недостаточно — данные всё равно в `tableData`).

## 3. Форма пользователя: учреждение и пароль

**Decision**: В редакторе Appsmith: поле учреждения → **Select** (`options` из `get_directory_inn`, label `short_name`, value `directory_inn_id`), поле пароля → **Password Input**. В `userAdmin.js` читать `CardForm.formData` (название формы по факту в форке).

**Rationale**: Фактически в `CardForm.json` форка: поле учреждения собрано как Text Input «ИНН» (accessor `directory_inn_id` — уже без пробела ✅, но не Select — нет options) — редактирование учреждения невозможно; пароль — Text Input (виден открытым текстом — нарушение SC-005). JS в форке уже читает `CardForm.formData` ✅ (в карточке фигурировала `JSONForm1` — расхождение карточки с форком, фиксируем факт форка).

**Alternatives considered**: Правка `widgets/*.json` напрямую ассистентом — запрещено конституцией III (только через редактор).

## 4. Удаление и блокировка

**Decision**: Оставить фактические `delete_user` (защита `has_sessions`/`has_history`) и `save_user` (гашение сессий при блокировке/смене пароля) без изменений — они покрывают FR-004/FR-005/FR-006.

**Rationale**: Сверено 20.09.2026 с телами в форке: логика соответствует спеке. Кнопка «ДА» в `deleteUserModal` уже подключена к `userAdmin.deleteUser()` (проверено по `Button4.json`) — замечание карточки п. 4 закрыто в форке.

**Alternatives considered**: Нет.

## 5. Прочее

- `userAdmin.js` фактически содержит 4 метода и читает `CardForm` — рефакторинг под другие имена не нужен.
- Проверка дубликата логина в JS должна исключать саму редактируемую запись (`u.id !== user_form.id`).
- Сравнение логинов — без учёта регистра (нормализация `toLowerCase()`), так как БД хранит `text` без точного регистра.
