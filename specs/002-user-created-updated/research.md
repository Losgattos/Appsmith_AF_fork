# Research: Даты учётных записей (создание/изменение)

**Feature**: `002-user-created-updated` | **Date**: 2026-09-23 | **Status**: Resolved

> **Дополнение 23.09.2026 (день) — правило проекта «время в МСК»:** JDBC-соединение Appsmith задаёт свой часовой пояс (GMT), игнорируя `server timezone` PostgreSQL. Смена timezone сервера на `Europe/Moscow` на приложение не влияет (проверено фактом: сессия Appsmith записала GMT при серверном Europe/Moscow). Решение пользователя: **все timestamp-значения проекта хранить явно в московском времени** — везде `now()` заменено на `(now() AT TIME ZONE 'Europe/Moscow')`: в DEFAULT `created_at`, функции `set_updated_at()`, SQL-телах 9 запросов (запись И сравнения). Существующие GMT-значения пересчитаны +3 ч (`testou4.created_at/updated_at`, 25 сессий `end_time`). Снапшоты `Appsmith_DB`: `d2cf892` (до) / `817a990` (после).

Факты собраны из: карточки [[Администрирование (Учётные записи)]] (решения 23.09.2026), снапшота `Appsmith_DB` (08_схема_ddl.sql), фактического состояния форка `Appsmith_AF_fork` (queries `get_users`, `save_user`), журнала дня.

## 1. Кто устанавливает даты (FR-003/FR-004)

**Decision**: Даты ведёт **база данных** (Вариант 3 из консультации 23.09.2026, решение пользователя): `created_at` — `DEFAULT now()` на колонке; `updated_at` — триггер `BEFORE UPDATE`. Приложение только читает и отображает даты; `save_user` не меняется.

**Rationale**:
- Дата создания всегда корректна, даже если INSERT выполнен вне формы (служебные скрипты, будущие импорты) — приложение может «забыть» передать значение.
- Дата изменения обновляется при **любом** способе правки (форма администрирования, прямой UPDATE через psql, будущие миграции данных) — не зависит от дисциплины вызова.
- Ноль изменений в JSObjects и SQL-телах существующих запросов `save_user` — меньше риск для работающего пилота.
- Единый тип `timestamp without time zone` — как во всей схеме (`user_sessions`, `user_log`, `report_status_history`); серверное время.

**Alternatives considered**:
1. Обе даты пишет приложение в `save_user` — отклонено: не покрывает правки мимо формы, требует правок в INSERT/UPDATE запросах, исторические записи без дат.
2. `created_at` пишет приложение, `updated_at` — БД (триггер) — отклонено: приложение может пропустить `created_at`; всё равно правки запросов.
3. **Обе даты — БД (DEFAULT + триггер)** — выбрано (см. выше).
4. Триггер на INSERT и UPDATE с полновесной логикой — отклонено: для INSERT достаточно DEFAULT; триггер на INSERT избыточен.

## 2. Формат и значения по умолчанию

**Decision**: `created_at timestamp without time zone NOT NULL DEFAULT (now() AT TIME ZONE 'Europe/Moscow')`; `updated_at timestamp without time zone` — без DEFAULT, nullable (NULL до первого изменения; уточнение 23.09.2026 вечером); бэкфилл существующих записей — `created_at = 2026-01-01 00:00:00`, `updated_at = NULL` (было `updated_at = DEFAULT now()` + бэкфилл обеих колонок 01.01.2026 — пересмотрено вечером 23.09.2026); триггер обновляет только `updated_at`. **23.09.2026 (день): DEFAULT и триггер-функция переведены на `(now() AT TIME ZONE 'Europe/Moscow')` — московское время явно, независимо от пояса сессии (см. шапку файла).**

**Rationale** (актуально после уточнения 23.09.2026 вечером):
- «Изменено» = «Создано» у новой записи выглядит нелогично (пользователь не правил запись) — поэтому `updated_at` без DEFAULT, при INSERT = NULL, в таблице пусто до первой правки.
- `created_at` остаётся NOT NULL DEFAULT now() — дата создания всегда известна.
- Бэкфилл: старые записи получают `created_at = 01.01.2026` (как раньше), а `updated_at` — NULL: мы не знаем, когда они менялись, честнее пусто, чем фиктивная 01.01.2026 («равно созданию»).
- Триггер срабатывает на любом UPDATE, включая правки мимо интерфейса — FR-004 сохраняется.
- **МСК-правило (23.09.2026, день):** `now()` в сессии Appsmith = GMT (JDBC задаёт свой пояс), поэтому `created_at`/`updated_at` писались на 3 часа меньше реального. `(now() AT TIME ZONE 'Europe/Moscow')` возвращает московское время независимо от пояса сессии — гарантированный результат для всех клиентов (psql, Appsmith, будущие).

**Alternatives considered**: `updated_at` без DEFAULT (заполняется только триггером при UPDATE) — первоначально отклонено из-за конфликта с `NOT NULL` на моменте создания. **Уточнение 23.09.2026 (вечер): реализовано именно это** — решение пользователя «„Изменено" заполняется только когда запись реально менялась»: `updated_at` без DEFAULT и без NOT NULL (Nullable), при INSERT = NULL, триггер заполняет при UPDATE; существующим записям бэкфилл `updated_at` сброшен в NULL (снапшоты `8b00d7e`/`ddde1d3`).

## 3. Функция и триггер

**Decision**: Общая функция `set_updated_at()` (plpgsql: `NEW.updated_at := now(); RETURN NEW;`), триггер `trg_users_updated_at BEFORE UPDATE ON appsmith.users FOR EACH ROW`; функция создаётся как `CREATE OR REPLACE` — переиспользуема для будущих таблиц (`directory_inn` в фиче «Управление учреждениями»).

**Rationale**: Единственный подходящий hook-момент для «изменено» — BEFORE UPDATE (гарантированно видит NEW). Переиспользование функции исключает дублирование кода при следующих фичах с датами.

**Alternatives considered**: Специализированный триггер с логикой внутри — отклонено (дублирование при будущих фичах); триггер AFTER UPDATE — отклонено (нельзя модифицировать строку, лишний проход).

## 4. Точки интеграции с приложением

**Decision**:
- `get_users.txt` (форк): добавить `u.created_at`, `u.updated_at` в SELECT — единственная правка файлов репозитория.
- `usersTable` (редактор Appsmith): добавить колонки «Создан»/«Изменён» с форматированием даты (правка только через редактор — принцип III).
- `save_user` INSERT/UPDATE: без изменений.

**Rationale**: `get_users` использует явный список колонок — без правки SELECT новые поля не попадут в `tableData`. Остальные запросы страницы дат не касаются.

**Alternatives considered**: `SELECT *` вместо явного списка — отклонено (теряется контроль за полями, в т.ч. риск вывода `password` — см. research 001).

## 5. Снапшоты и документация БД (принцип IV)

**Decision**: Снапшот `Appsmith_DB` **до** и **после** миграции (по существующему механизму через psql, заметка «Схема БД»/карточка psql); актуализация Grammax 51 «Структура БД» (обновить таблицу `users` на добавленные колонки); заметка [[Схема БД]] рабочего слоя.

**Rationale**: Изменение структуры БД — обязательный триггер снапшотов по конституции IV; страница 51 — единственная, ведущаяся сразу в Grammax.

**Alternatives considered**: — (обязательное правило).

## 6. Верификация дат (quickstart)

**Decision**: Проверки в редакторе Appsmith (колонки отображаются, новые записи получают даты, правка обновляет «Изменён» и не трогает «Создан») + прямые SQL-проверки через psql (бэкфилл = 01.01.2026; UPDATE мимо интерфейса обновляет `updated_at`).

**Rationale**: Проект без автотестов; двухконтурная проверка (UI + данные) покрывает FR-003…FR-008 независимо от форматирования в редакторе.

**Alternatives considered**: Проверка только в UI — недостаточно (не доказывает триггер на правках мимо формы).
