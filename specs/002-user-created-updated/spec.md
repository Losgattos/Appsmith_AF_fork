# Feature Specification: Даты учётных записей (создание/изменение)

**Feature Branch**: `002-user-created-updated`

**Created**: 2026-09-23

**Status**: Implemented

**Input**: User description: "Добавить учётной записи дату создания и дату изменения. Для существующих записей заполнить дату 1 января 2026 года. Даты вывести в таблицу списка учётных записей."

## Clarifications

### Session 2026-09-23

- Q: Как фиксировать даты — на уровне приложения или базы данных? → A: **На уровне базы данных (Вариант 3 — эталон практики):** дата создания — значение по умолчанию базы (не задаётся приложением), дата изменения — обновляется базой автоматически при любом изменении записи. Приложение только читает и отображает даты. (Решение пользователя 23.09.2026.)
- Q: Чем заполнить даты существующих записей (созданных до фичи)? → A: **1 января 2026 года** — единое фиксированное значение для всех существующих записей. (Решение пользователя 23.09.2026.)
- Q: Где показывать даты? → A: В **таблице списка учётных записей** страницы администрирования — отдельными видимыми колонками «Создан» и «Изменён». (Решение пользователя 23.09.2026.)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Дата создания и дата изменения видны администратору (Priority: P1)

Администратор открывает страницу администрирования; в таблице списка учётных записей он видит для каждой записи дату создания и дату последнего изменения. Даты заполнены для всех записей (включая созданные до внедрения фичи).

**Why this priority**: Это единственная цель фичи — прозрачность жизненного цикла учётной записи для администратора; без отображения фича не приносит пользы.

**Independent Test**: Открытие страницы под администратором и визуальная проверка колонок «Создан»/«Изменён»: каждая строка содержит обе даты, у существующих записей — 01.01.2026.

**Acceptance Scenarios**:

1. **Given** страница администрирования открыта под администратором, **When** просматривается таблица учётных записей, **Then** каждая строка содержит дату создания и дату последнего изменения.
2. **Given** учётная запись создана до внедрения фичи, **When** администратор смотрит её строку, **Then** обе даты равны 01.01.2026.
3. **Given** учётная запись создана после внедрения фичи, **When** администратор смотрит её строку, **Then** дата создания не пустая и соответствует фактическому моменту создания.

---

### User Story 2 - Дата изменения обновляется автоматически (Priority: P1)

Администратор редактирует учётную запись (меняет роль, логин, учреждение, статус активности или пароль). После сохранения дата изменения этой записи в таблице обновляется на момент правки; дата создания не меняется.

**Why this priority**: Без автоматического обновления дата изменения бесполезна — требование гарантирует корректность независимо от способа правки (форма, прямой доступ к данным, будущие импорты).

**Independent Test**: Изменение любого поля пользователя через форму редактирования → видимая дата изменения обновляется, дата создания остаётся прежней; изменение записи вне интерфейса (например, служебным скриптом) также обновляет дату изменения.

**Acceptance Scenarios**:

1. **Given** существующая учётная запись, **When** администратор изменяет любое её поле и сохраняет, **Then** дата изменения обновляется на момент сохранения, дата создания не изменяется.
2. **Given** учётная запись, **When** в её данные вносятся изменения любым способом (в том числе помимо формы администрирования), **Then** дата изменения обновляется автоматически, без дополнительных действий.
3. **Given** учётная запись, **When** она не изменялась с момента создания, **Then** дата изменения пуста (не показывается), пока запись не будет изменена (уточнение 23.09.2026 вечером).

---

### Edge Cases

- Записи, созданные до фичи: дата создания = 01.01.2026 (решение пользователя); дата изменения — пустая (NULL), пока запись не правят; после первой правки дата изменения станет фактической, дата создания останется 01.01.2026.
- Массовое служебное обновление множества записей (например, восстановление данных): дата изменения сдвинется у всех затронутых записей — ожидаемое поведение, в рамках фичи не ограничивается.
- Пустой пароль при редактировании («не менять»): с 22.09.2026 пароль обязателен всегда, отдельный кейс не требуется; если правка сохранена — дата изменения обновляется.
- Отображение даты для записей с ещё не установленным значением: «Изменено» показывается пустым до первой правки (уточнение 23.09.2026 вечером); «Создано» непусто всегда.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST хранить для каждой учётной записи дату создания.
- **FR-002**: Система MUST хранить для каждой учётной записи дату последнего изменения.
- **FR-003**: Система MUST устанавливать дату создания автоматически в момент создания учётной записи (без участия приложения или администратора).
- **FR-004**: Система MUST автоматически обновлять дату изменения при любом изменении учётной записи — независимо от способа изменения (интерфейс, служебные операции, будущие импорты).
- **FR-005**: Дата создания MUST NOT изменяться при последующих правках учётной записи.
- **FR-006**: Система MUST присвоить существующим (созданным до фичи) учётным записям дату создания 01.01.2026; дата изменения для них не фиксируется (пустая, уточнение 23.09.2026 вечером: «Изменено» заполняется только при реальном изменении).
- **FR-007**: Система MUST отображать обе даты в таблице списка учётных записей страницы администрирования в виде отдельных колонок «Создан» и «Изменён», понятных администратору.
- **FR-008**: Дата создания MUST быть непустой для всех учётных записей после внедрения фичи; дата изменения может быть пустой до первой правки записи (уточнение 23.09.2026 вечером).

### Key Entities *(include if feature involves data)*

- **Учётная запись (пользователь)**: к существующим атрибутам (логин, пароль, роль, учреждение, статус активности) добавляются дата создания и дата последнего изменения. Это единственное изменение сущности в данной фиче.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% учётных записей (включая созданные до фичи) имеют непустую дату создания после внедрения; дата изменения непуста у записей, которые изменялись (уточнение 23.09.2026 вечером: до первой правки «Изменено» пустое).
- **SC-002**: 100% существовавших до фичи записей показывают дату создания 01.01.2026 до первой правки.
- **SC-003**: 100% правок учётной записи (через форму или любым другим способом) обновляют дату изменения; ни одна правка не изменяет дату создания.
- **SC-004**: Администратор видит даты создания и изменения в таблице без дополнительных действий (без переключения вкладок, модальных окон или отдельных запросов).

## Assumptions

- Изменение затрагивает только учётные записи (`users`); справочники (учреждения, роли) в этой фиче не получают дат — это отдельная будущая фича «Управление учреждениями».
- Формат отображения дат в UI: дата и время в читаемом виде (например, «01.01.2026 00:00»), конкретное оформление колонки — в редакторе Appsmith.
- Тип хранения времени — единый с остальной схемой проекта (значения без временной зоны), **значения хранятся в московском времени явно** — `now() AT TIME ZONE 'Europe/Moscow'` во всех местах записи и сравнения (правило проекта, решение пользователя 23.09.2026; причина: JDBC-соединение Appsmith работает в GMT и игнорирует server timezone — проверено фактом).
- Механизм автоматического обновления даты изменения реализуется на уровне базы данных (решение пользователя 23.09.2026); переиспользуется для будущих фич при необходимости.
- Реализация происходит в низкокодовой среде (Appsmith) поверх существующего приложения; способы реализации вынесены в план и не могут противоречить конституции проекта (принципы I–V).
