# Quickstart: Даты учётных записей (создание/изменение)

**Feature**: `002-user-created-updated` | **Date**: 2026-09-23

Сценарии валидации фичи «end-to-end». Двухконтурная проверка: **UI (редактор Appsmith)** + **данные (psql)**.

**Прогон 23.09.2026: все сценарии подтверждены** (psql-часть — copilot, UI-часть — пользователь в редакторе после Pull; результаты в журнале дня 23.09). **Вечером 23.09.2026 поведение уточнено (решение пользователя):** «Изменено» заполняется только при реальном изменении записи — при создании `updated_at = NULL` (в UI пусто), у существующих записей прошлый бэкфилл `updated_at` обнулён; сняты снапшоты `Appsmith_DB` `8b00d7e` (до) / `ddde1d3` (после), верификация INSERT/UPDATE повторена. **Днём 23.09.2026 (решение пользователя — правило проекта):** время везде хранится в МСК явно — `(now() AT TIME ZONE 'Europe/Moscow')` в DEFAULT/триггере/запросах, существующие GMT-значения пересчитаны +3 ч (снапшоты `d2cf892` / `817a990`). ⚠️ При проверках psql сравнивайте значения с **текущим московским временем**, а не с `now()` — psql-сессия может быть в любом поясе.

## Prerequisites

- Доступ к PostgreSQL через psql работает (карточка «Доступ к PostgreSQL (psql).md»).
- Снапшот `Appsmith_DB` «до» снят и закоммичен (принцип IV).
- В редакторе Appsmith выполнен **Pull** (после push форка пользователем), затем проверки ниже.

## Сценарий 1. Бэкфилл существующих записей (данные)

**When**: миграция выполнена (23.09.2026 — базовая; вечером того же дня применена корректировка: `updated_at` обнулён).
**Then**:
- до корректировки: `created_at = updated_at = 2026-01-01 00:00:00`;
- после корректировки (актуально): `created_at = 2026-01-01 00:00:00`, `updated_at = NULL` у записей, не правившихся после неё.

Проверка через psql:

```sql
SELECT login, created_at, updated_at FROM appsmith.users ORDER BY id;
-- ожидаемо: created_at = 2026-01-01 00:00:00, updated_at = NULL (до первых правок)
```

**Ожидаемый результат**: у старых записей нет NULL в `created_at` и нет значений now()/01.01.2026 в `updated_at` (он пустой до первой правки).

## Сценарий 2. Новая запись получает даты от БД (UI + данные)

**When**: администратор создаёт нового пользователя через форму (Добавить → заполнить → Сохранить).
**Then**:
- в таблице `usersTable` у новой строки заполнена колонка «Создан», колонка «Изменён» — пустая;
- в БД: `created_at` = московское время создания, `updated_at` = NULL (уточнение 23.09.2026 вечером; время в МСК — правило 23.09.2026, день).

Проверка через psql:

```sql
SELECT login, created_at, updated_at FROM appsmith.users WHERE login = '<новый логин>';
```

**Ожидаемый результат**: `created_at` непустой, `updated_at` = NULL.

## Сценарий 3. Правка обновляет «Изменён», но не «Создан» (UI + данные)

**When**: администратор редактирует пользователя (например, меняет роль или статус активности) и сохраняет.
**Then**:
- в таблице у строки заполнилась/обновилась колонка «Изменён», колонка «Создан» не изменилась;
- в БД: `updated_at` стал непустым (момент первой правки) и новее прежнего значения; для новых записей `updated_at > created_at`; для старых (бэкфилл) `updated_at` = момент правки, `created_at` = 01.01.2026.

Проверка через psql (до/после правки):

```sql
SELECT login, created_at, updated_at FROM appsmith.users WHERE login = '<логин>';
-- записать значения до правки, повторить после: updated_at изменился, created_at — нет
```

**Ожидаемый результат**: `updated_at` вырос (из NULL или старого значения), `created_at` без изменений.

## Сценарий 4. Триггер при правке мимо интерфейса (данные)

**When**: запись `users` обновляется напрямую через SQL (не через форму Appsmith):

```sql
UPDATE appsmith.users SET is_user_enabled = true WHERE login = '<логин>';
```

**Then**: `updated_at` обновился автоматически (триггер), `created_at` не тронут.

```sql
SELECT login, created_at, updated_at FROM appsmith.users WHERE login = '<логин>';
```

**Ожидаемый результат**: `updated_at` = момент UPDATE, `created_at` прежний.

> ⚠️ **Проверять UPDATE в ОТДЕЛЬНОЙ транзакции (автокоммит), а не в одной с INSERT**: в PostgreSQL `now()` — константа в пределах транзакции, поэтому INSERT+UPDATE в одной транзакции дадут одинаковые значения (триггер технически отработал, но записал то же `now()`). Наблюдение зафиксировано при прогоне 23.09.2026 (была ложная тревога «триггер не сработал»).

## Сценарий 5. Отображение колонок в таблице (UI)

**When**: страница «Администрирование» открыта под администратором.
**Then**: в `usersTable` видны колонки «Создан»/«Изменён» с читаемым форматом даты (дата+время), для старых записей — «Создан» 01.01.2026, для новых — фактические даты; «Изменён» пустой у записей, которые не правили (уточнение 23.09.2026 вечером).

**Ожидаемый результат**: колонки видны, форматы читаемы, пароль нигде не отображается (регресс-контроль FR-001).

## Регресс (короткий прогон пилота)

- Вход новым пользователем по заданным данным — проходит (механизм сессий не затронут).
- Блокировка пользователя завершает активные сессии (save_user не менялся — регресс не ожидается).
